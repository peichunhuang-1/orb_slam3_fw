# orb_extractor

fw block `OrbExtractor`: ORB features (ORB-SLAM3 conventions) of an image, on the GPU (Vulkan compute) or
the CPU. Both backends give the same keypoints; see "GPU vs CPU" below for the last-bit differences.

| Port | Type | |
|---|---|---|
| `image` (trigger) | `fw::Image` | mono8 (any `CV_8UC1`), bgr8 / rgb8 / bgra8 / rgba8 |
| `params` (latest, optional) | `OrbExtractorParams` | `params/orb_extractor_params.hpp`, example `config/orb_extractor.yaml` |
| `features` | `orb::Features` | keypoints (full resolution, octave = level), N x 32 `CV_8U` descriptors (cv::ORB layout) |

```yaml
blocks:
  orb: { algorithm: OrbExtractor }
edges:
  - cam.left -> orb.image
  - config://orb_extractor.yaml -> orb.params
```

`backend`: `auto` (GPU, the CPU if the GPU cannot be used, reported as degraded), `gpu`, `cpu`.

## Files

| Path | |
|---|---|
| `orb_extractor.cpp` | the block |
| `orb_cpu.hpp/.cpp` | CPU implementation (no fw dependency); the CPU reference for the GPU |
| `vk/orb_vk.*` | GPU engine `OrbVk` (Vulkan 1.1 compute) |
| `vk/orb_vk_slam.*` | `ORBextractorVk`: ORB-SLAM3's interface and threshold policies on top of `OrbVk` |
| `vk/shaders/` | compute shaders, compiled to SPIR-V headers by CMakeLists.txt; blur / fast / fast_full / harris are generated by `vk/tools/gen_shaders.py` |
| `docs/ALGORITHM.md`, `docs/GPU_PROFILING.md` | GPU algorithm and tuning notes (from the original stand-alone project; its tools `orb_demo` etc. are not part of this package) |

The Vulkan backend is built when CMake finds Vulkan and `glslangValidator` (the dev container has both);
otherwise only the CPU backend is built. The dev container builds Mesa's v3dv for the Pi 5
(`.devcontainer/Dockerfile`) and passes the GPU in (`--device=/dev/dri`, `.devcontainer/gpu_access.sh`).
The image sets `V3DV_CSD_MAX_SG_ID=15`, the patched driver's faster compute scheduling (1.6-1.8x per
image, same results); `V3DV_CSD_MAX_SG_ID=-1` (or unset) gives stock Mesa behaviour.

## GPU vs CPU

```bash
build/orb_slam3_fw/orb_gpu_vs_cpu [--allow-cpu] [image.pgm ...]
```

Positions, responses, octaves, sizes and order are identical. GLSL's `atan` / `cos` / `sin` are not
correctly rounded, so angles can differ in the last bits and a descriptor bit whose rotated sample sits at
a rounding boundary can flip (llvmpipe, 49k keypoints: max 0.0002 deg, 16 descriptors with 1-2 bits).
The GPU's corner and keypoint lists are bounded (pixel noise overflows them; `abort_corner_fraction`
makes such frames abnormal); the CPU's are not. With `per_cell_threshold: false` both use the fixed
`ini_th_fast` (the GPU engine's adaptive threshold is off in this block).
